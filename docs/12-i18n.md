# 12 — Internationalisation (i18n)

## 12.1 Goal

The language is **explicitly resolved** instead of being read from whatever
locale the JVM happens to have (request parameter, configuration, desktop
language, English as the last resort — see §12.6), and every user-visible text
can be translated without touching the code.

Two things follow from that:

1. **English is not a translation file.** The English text *is* the message id
   (the classic gettext convention), so there is no key catalogue to keep in
   sync and nothing to translate for the source language.
2. **The OS locale must not leak in — it may only be asked.** Earlier builds
   showed German texts although our sources contain no German at all: they came
   from **autumo-ui**, whose `Helper.getMessageBundle()` calls
   `ResourceBundle.getBundle(basename)` *without* a locale and therefore picks
   up the JVM default locale — on this machine `de_CH` →
   `Bundle_de_CH.properties`. Today the framework resolves the language it was
   *told* (`Helper.setLanguage(…)`), and §12.6 is the single place that consults
   the desktop locale, as the second to last candidate.

## 12.2 Why PO files

PO (gettext) was chosen over `.properties`:

| | `.properties` | **PO** |
|---|---|---|
| Plural forms | manual | `msgid_plural` / `msgstr[n]` |
| Contexts (same English word, different meaning) | not possible | `msgctxt` |
| Translator comments, source references | awkward | `#.`, `#:`, `# ` |
| Tooling | editors only | Poedit, Weblate, Crowdin, Lokalize, … |
| Fuzzy matching on source changes | none | `#, fuzzy` |

The PO files are read at runtime by a **small own reader** (no dependency, no
code generation step). Since the review round, the reader is part of the
**autumo-ui framework** — PO is a framework feature that *any* autumo-ui
application can use, not a Studio specialty:

* `ch.autumo.ui.utils.PoFile` — the parser,
* `ch.autumo.ui.utils.PoResourceBundle` — a `ResourceBundle` that **merges** the PO
  catalogues of several base resource paths (the application's first, then the
  framework's),
* wired into `Helper.getMessageBundle(…)`, so the framework's own lookup
  (`Helper.getTranslatedText(app, …)`) resolves PO keys as well.

There is **no `.properties` language file left anywhere** — also not in
autumo-ui: the framework's own `ch/autumo/ui/lang/Bundle{,_de,_en_US}.properties`
became `messages.pot` / `messages.en.po` / `messages.de.po` in the same package.
An application therefore ships *only* the PO files of its own texts; the
framework's keys (its panes, dialogs, the installer, the window title) come from
the framework catalogue and are merged in automatically (§12.9.1).

The Studio itself only keeps a thin facade, `ch.autumo.ifacex.studio.ui.Messages`
(§12.4), because it adds conventions on top of the lookup (msgid = English text,
fallback variant for metadata labels). The old `core/i18n` package is gone.

`PoFile` already understands `msgctxt` (and keys such an entry as
`context + '\0' + msgid`), but the application currently has no ambiguous English
word that needs a context, so the lookup API does not expose one yet. Adding
`t(id, context, fallback)` later is a local change.

## 12.3 Layout

```
ui/src/main/resources/ch/autumo/ifacex/studio/ui/lang/
    messages.pot        # template: every msgid, empty msgstr (translator reference)
    messages.en.po      # only the framework-key overrides (see §12.6)
    messages.de.po      # German translation

(autumo-ui, the framework catalogue, same layout below /ch/autumo/ui/lang/)
    messages.pot        # the framework's own texts
    messages.en.po
    messages.de.po
```

* `messages.pot` mirrors the code and is the **hand-over file** for translators
  (it lists all messages, including the ones not translated yet).
* `messages.<lang>.po` is loaded from the classpath; a missing file simply means
  "no catalogue for that language".
* The catalogue sits at the Studio's **application base resource path**
  (`/ch/autumo/ifacex/studio/ui/`), because that is where the framework looks for
  it (`<base>/lang/messages.<lang>.po`, see `PoResourceBundle`). The Studio ships
  **no** `lang/Bundle*.properties` any more — and neither does autumo-ui.
* `Messages.LANGUAGES` lists the languages that ship a catalogue (extend it when
  another PO is added).

## 12.4 Usage

```java
import static ch.autumo.ifacex.studio.ui.Messages.format;
import static ch.autumo.ifacex.studio.ui.Messages.t;

label.setText(t("Add standard mapping"));                    // plain message
status.setText(format("Saved {0} ({1})", name, extension));  // with arguments
tooltip = new Tooltip(t("Create a new, empty configuration"));
```

Rules for new code:

* **Every** user-visible string goes through `t(…)` or `format(…)` — never a raw
  literal in a `Label`, `Button`, `Tooltip`, `TableColumn`, dialog or status line.
* `format(…)` uses `java.text.MessageFormat`, so `{0}`, `{1}`, … are arguments.
  **A message that contains literal braces must not go through `format(…)`** —
  MessageFormat would read `{source-field-1}` as an argument number. The mapping
  validation splits such a message into a `format(…)` part (the wrong value) and a
  `t(…)` part (the example with braces); see `FormBuilder.addMappingFromBox`.

## 12.5 Parameter labels

The metadata forms (`FormBuilder.mapGrid`) do not use the English label as the
message id — that label is *derived* from the configuration key and would change
whenever the derivation changes. Instead:

* the **message id is the raw configuration key** (e.g. `data_path`),
* the **derived English label is the fallback** (`t(id, english)`),

so a translation file can translate a parameter by its stable key and anything
not translated simply stays as it is:

```java
final String label = t(key, FieldCatalog.descriptor(key).label());   // "Datenpfad" or "Data path"
final Tooltip tip = new Tooltip(t(key + ".help", descriptor.help())); // help text: "<key>.help"
```

In the PO file such an entry carries the English label as an extracted comment:

```po
#. Data path
msgid "data_path"
msgstr "Datenpfad"

#. Path to the data array within the JSON response.
msgid "data_path.help"
msgstr "Pfad zum Daten-Array in der JSON-Antwort."
```

The keys are **technical identifiers and are never translated**; only their
labels and help texts are. Because the derived label is always shown when a
translation is missing, the parameter list in the catalog can grow without ever
leaving a field unlabelled.

## 12.6 Switching the language

The language is resolved **once at startup**, before the FXML is loaded
(`StudioApp.preInitialize`), in this order:

| Priority | Source | Example |
|---|---|---|
| 1 | system property | `-Dapp.lang=de` |
| 2 | app configuration `language` (autumo-ui `Constants.PROP_KEY_LANGUAGE`) | `language=de` in `ui/.../cfg/app.cfg` |
| 3 | app configuration `lang` (alias) | `lang=de` |
| 4 | desktop language (`Locale.getDefault()`, e.g. `de_CH` → `de`) | a Swiss German desktop → `de` |
| 5 | last resort | `en` |

The first candidate that carries a value wins; an empty or absent key is
skipped. The shipped `cfg/app.cfg` leaves the key **commented out**
(`#language=`), so a fresh install follows the desktop language and nothing
else. Priority 5 also catches *explicit* values that are not supported: a
French desktop, `language=fr` or `-Dapp.lang=fr` have no PO catalogue and
therefore end up English, exactly like a blank value.

`Messages.setLanguage(…)` delegates to `Helper.setLanguage(…)`, which sets
`Locale.setDefault(…)` and the `user.language` system property, so the framework
(autumo-ui dialogs, the window title) follows the resolved language to the end,
and reports how many entries the catalogue carries.

**Nothing is written *into* the template.** A language the user picks in the GUI
is stored as `language=<code>` in the **application configuration** of the user
(`app.cfg` in the application data directory — on macOS
`~/Library/Application Support/autumo/ifaceXStudioFX/cfg/app.cfg`), next to
everything else autumo-ui keeps there. `Help › Language` writes it
(`BaseApp.setConfigurationParameter`), and priority 2 reads it back on the next
start. That file is created by autumo-ui's **installer phase**
(`InstallAction` → `BaseApp.completed`), which runs on the first start because the
Studio is **not** a portable app since 2026-10-18 — see doc 07 §7.5 (Decisions Log).
Changes made while the app runs live in memory and are persisted by
`BaseApp.storeProps()`: `Help › Language` calls it right after storing the code, so
the switch is written at once, and the app exit writes it anyway (like the recent
files). Before the wizard has run there is no such file: the language then follows
the desktop (or `-Dapp.lang`).

**English needs no real translation file:** English *is* the source language, so
for every normal message the `msgstr` would just repeat the `msgid` — `t(…)`
simply returns the message id (the English text) when the lookup finds nothing. A
language without a PO file behaves the same way. `messages.pot` is the template
that lists every message for translators.

The Studio's `messages.en.po` exists nevertheless, but it carries **only the
framework-key overrides**: keys such as `application.name` and `About.title` are
*not* English text, so their English value has to be stored somewhere. Everything
else in `messages.en.po` would be redundant. The framework's own
`messages.en.po` is a real catalogue, because its keys (`button.Alright`,
`menu.File`, `Installer.next`, …) are keys as well and not English texts.

> Note: neither the Studio nor autumo-ui ships a `lang/Bundle*.properties` any
> more. Both catalogues are PO files and are **merged** — the application's file is
> looked up first, the framework's (`ch/autumo/ui/lang/messages.<lang>.po`) after
> it — so framework keys the Studio does not override still resolve, and the Studio
> may override any framework text (see §12.9.1).

## 12.9 Live language switch (`Help › Language`)

Because §12.6 resolves the language only once at start-up, a running instance
could not be re-texted: a user who started the Studio in English on a German
machine had to quit and restart it with `-Dapp.lang=de`. The application now
offers the language at runtime: **`Help › Language ›` English / Deutsch**, each
with the framework's 16px flag icon (`lang_en.png` / `lang_de.png`). The `Language`
menu itself carries the framework's 16px language icon — now the Phosphor `translate`
glyph (with a fall-back to the legacy `language-16.png`), set by `initializeLanguageMenu`
unless the application has already put its own graphic on the menu). The language
names are written in their own language and are *not* translated. The switch
applies to the running instance **and** is remembered: `language=<code>` goes
into the user's application configuration, so the next start comes up in the same
language (§12.6) — as soon as the Studio has that file, i.e. once it is installed
and no longer `isPortableApp()`.

**The switch itself is a framework feature.** `BaseController` owns the menu and
the mechanism; the Studio implements only its own re-texting hook:

```java
// autumo-ui, ch.autumo.ui.fx.controller.BaseController
protected void initializeLanguageMenu(Menu menu);   // one radio item per Helper.getSupportedLanguages()
public void switchLanguage(String lang);            // Helper.setLanguage + window title + persist + hook
protected void languageChanged();                   // default: empty

// Studio, ch.autumo.ifacex.studio.ui.MainController
initializeLanguageMenu(menuLanguage);               // in init(), replaces the FXML items
@Override protected void languageChanged() { applyTexts(); buildToolBar(); … }
```

`BaseController.switchLanguage(lang)` moves the framework catalogue
(`Helper.setLanguage(lang)`: JVM default locale + `user.language` + the bundle
cache), re-titles the stage, stores `language=<code>` through
`setConfigurationParameter(Constants.PROP_KEY_LANGUAGE)` + `storeProps()`, marks
the radio item and finally calls the hook. The hook `languageChanged()` has an
**empty default implementation** instead of being abstract, so applications that
were written before this feature (autumo-ui-demo, autumo-documents-ui,
autumo-portals) still compile and run — only an application with texts of its own
overrides it (see doc 07 §7.5).

The Studio's hook re-runs `applyTexts()` (static FXML shell), `buildToolBar()` and
— when a configuration is open — `rebuild()` (navigation tree and the visible
form), and re-renders the status bar, so no stale text is left anywhere.
`Help › Language` marks the active language with a radio dot; the selection is
applied programmatically at start-up, which does **not** fire `onAction` in
JavaFX.

### 12.9.1 One mechanism: PO lives in the framework, catalogues are merged

This answers an open question from the review: *should PO support move into
autumo-ui?* — **Yes, it did** (see §12.2), and the framework carries **only PO**
files:

* The **framework catalogue** `ch/autumo/ui/lang/messages.<lang>.po` replaced
  `Bundle{,_de,_en_US}.properties`. `Helper.getTranslatedText(app, "About.title")`,
  the framework's FXML panes (`defaultInfoPane.fxml`…) and its dialogs all resolve
  through it.
* The **application catalogue** is PO as well and is resolved **by the framework**
  at the application base resource path (`ui/…/ui/lang/messages.*.po`).
* `Helper.getMessageBundle(base)` **merges** both: the application's PO first, the
  framework's after it (`PoResourceBundle(lang, appBase, Constants.BASE_RESOURCE_PATH)`,
  first catalogue wins) and caches the result per base + language. A framework key
  the application does not define resolves from the framework; an application that
  defines it overrides the framework text. An application without any PO file is
  not an error.
* `core` is UI-free: the old `core/i18n` package (parser + lookup) was deleted;
  the parser moved into autumo-ui.

> Consequence: any *other* autumo-ui application that still ships
> `lang/Bundle*.properties` (autumo-ui-demo, autumo-documents-ui, autumo-portals,
> …) would come up with raw message ids, because the framework no longer reads
> `.properties`. Migrating them is a one-off conversion of their bundle into
> `messages.<lang>.po` — a separate change in those repositories; the Studio does
> not need anything from them.

The framework changes (all in autumo-ui, version stays `1.2.0`):

* `Helper.setLanguage/getLanguage/getSupportedLanguages/addLanguageListener` —
  the language is now an explicit framework state instead of being read ad-hoc
  from `user.language`. A region is ignored (`de_CH` → `de`), which matters
  because autumo-ui's own `Constants.LOCALE_DE` *is* `de_CH`.
* `Helper.getMessageBundle()` returns a **`PoResourceBundle`**: the application's
  PO catalogue (`<base>/lang/messages.<lang>.po`, parsed by the new
  `ch.autumo.ui.utils.PoFile`) is consulted first, the framework's catalogue
  (`/ch/autumo/ui/lang/messages.<lang>.po`) fills the rest — see the merge above.
  The bundle is cached per base/language and the cache is cleared on a language
  change (`Helper.setLanguage`), so the PO files are parsed once and not on every
  lookup. An application without a PO catalogue is not an error.
* `BaseController.initializeLanguageMenu/switchLanguage/languageChanged` (§12.9) —
  the `Help › Language` menu and the runtime switch, so an application does not
  implement it again. The framework's own texts follow because `switchLanguage`
  calls `Helper.setLanguage` and re-titles the stage; the application re-texts
  itself in the `languageChanged()` hook.
* `Helper.getText(app, id, fallback)` — a lookup that returns a fallback instead
  of throwing `MissingResourceException`. Needed for the Studio's metadata-driven
  texts, whose message id is a configuration key (§12.5).
* The framework's catalogues are `messages.en.po` / `messages.de.po`; the bundled
  HTML panes read the language through `Helper.getLanguage()`.
* `ch.autumo.ui.utils.FallbackResourceBundle` is **deleted** — the parent-bundle
  mechanism it implemented is replaced by the merge inside `PoResourceBundle`.
* `UI.showExceptionDialogExtended` now styles itself with the autumo-ui base
  stylesheet. Before, it built an app path (`<app>/style/application.css`) that
  no application ships, so the global uncaught-exception handler – installed by
  `BaseApp` for every app – ended in an `NullPointerException`.
* `Helper.getBaseStyleURL()` / `Helper.getBaseHTMLStyleURL()` had swapped
  bodies (the JavaFX stylesheet vs. the WebView stylesheet); they now match
  their names.

One dependency followed from this: the Studio's `ui` module must ship
`javafx-web` (Gradle) because the framework renders About/license in a `WebView`;
without it the panes fail with `NoClassDefFoundError`/`ClassNotFoundException`.

## 12.10 Live switch and shell in the UI tests

The former `Launcher --selftest` mode (it printed the rendered navigation labels,
the status line, a sample of the parameter labels and the result of a language
switch) is gone: test code belongs into the test sources. `StudioUiTest`
(`ui/src/test/java/ch/autumo/ifacex/studio/ui/`) builds the **real shell** instead
— `StudioApp.preInitialize(stage, props)` on the JavaFX application thread with
`main.fxml`, the framework scene and `style/application.css` — and asserts on it:

| Test | Covers |
|---|---|
| `shellIsBuiltWithTheFrameworkLanguageMenu` | window, style sheets, the framework's language items (count, selection), menu texts, status bar |
| `toolbarButtonsResolveTheirIcons` | every toolbar button carries a loadable icon |
| `interFontIsLoaded` | the Inter family is registered (`StudioApp.loadFonts`) |
| `everyNavigationEntryBuildsItsForm` | the sample config loads, every navigation entry renders a form, source field lists, the mapping table and its dnd buttons exist, parameter labels resolve through the message lookup |
| `rawViewsAndStatusShowTheLoadedConfiguration` | both raw views carry the loaded configuration, the status bar names the file |
| `languageSwitchRetranslatesStudioAndFramework` | the framework switch moves the Studio's texts (`File` → `Datei`), the framework's texts (`button.Alright` → `Okay`) and the menu selection — and switches back |
| `languageSwitchIsStoredInTheApplicationConfiguration` | `language=<code>` reaches `cfg/app.cfg` and `BaseApp.getConfigurationParameter` |
| `frameworkPanesOpenInEveryLanguage` | About, Encoder and License panes build and show in both languages; the per-language HTML resources exist |

The Gradle test JVM of the `ui` module runs with a scratch `user.home`
(`build/test-home`, `systemProperty 'user.home'` in `ui/build.gradle`); the tests create the
`cfg/app.cfg` of that home themselves, so the persistence check never touches the
developer's real configuration — and the same test class starts the toolkit once
(`Platform.startup`) and closes the shell in `@AfterAll`, restoring the desktop
locale.
