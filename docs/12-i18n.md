# 12 — Internationalisation (i18n)

## 12.1 Goal

The application is **English by default and independent of the operating
system locale**, and every user-visible text can be translated without touching
the code.

Two things follow from that:

1. **English is not a translation file.** The English text *is* the message id
   (the classic gettext convention), so there is no key catalogue to keep in
   sync and nothing to translate for the source language.
2. **The OS locale must not leak in.** Earlier builds showed German texts
   although our sources contain no German at all: they came from **autumo-ui**,
   whose `Helper.getMessageBundle()` calls `ResourceBundle.getBundle(basename)`
   *without* a locale and therefore picks up the JVM default locale — on this
   machine `de_CH` → `Bundle_de_CH.properties`.

## 12.2 Why PO files

PO (gettext) was chosen over `.properties`:

| | `.properties` | **PO** |
|---|---|---|
| Plural forms | manual | `msgid_plural` / `msgstr[n]` |
| Contexts (same English word, different meaning) | not possible | `msgctxt` |
| Translator comments, source references | awkward | `#.`, `#:`, `# ` |
| Tooling | editors only | Poedit, Weblate, Crowdin, Lokalize, … |
| Fuzzy matching on source changes | none | `#, fuzzy` |

The PO files are read at runtime by a **small own reader** (no dependency, no
code generation step). Since the review round, the reader is part of the
**autumo-ui framework** — PO is a framework feature that *any* autumo-ui
application can use, not a Studio specialty:

* `ch.autumo.ui.utils.PoFile` — the parser,
* `ch.autumo.ui.utils.PoResourceBundle` — a PO-first `ResourceBundle`,
* wired into `Helper.getMessageBundle(…)`, so the framework's own lookup
  (`Helper.getTranslatedText(app, …)`) resolves PO keys as well.

The Studio itself only keeps a thin facade, `ch.autumo.ifacex.studio.ui.Messages`
(§12.4), because it adds conventions on top of the lookup (msgid = English text,
fallback variant for metadata labels). The old `core/i18n` package is gone.

`PoFile` already understands `msgctxt` (and keys such an entry as
`context + '\0' + msgid`), but the application currently has no ambiguous English
word that needs a context, so the lookup API does not expose one yet. Adding
`t(id, context, fallback)` later is a local change.

## 12.3 Layout

```
ui/src/main/resources/ch/autumo/ifacex/studio/ui/lang/
    messages.pot        # template: every msgid, empty msgstr (translator reference)
    messages.en.po      # only the framework-key overrides (see §12.6)
    messages.de.po      # German translation
```

* `messages.pot` mirrors the code and is the **hand-over file** for translators
  (it lists all messages, including the ones not translated yet).
* `messages.<lang>.po` is loaded from the classpath; a missing file simply means
  "no catalogue for that language".
* The catalogue sits at the Studio's **application base resource path**
  (`/ch/autumo/ifacex/studio/ui/`), because that is where the framework looks for
  it (`<base>/lang/messages.<lang>.po`, see `PoResourceBundle`). The Studio ships
  **no** `lang/Bundle*.properties` any more.
* `Messages.LANGUAGES` lists the languages that ship a catalogue (extend it when
  another PO is added).

## 12.4 Usage

```java
import static ch.autumo.ifacex.studio.ui.Messages.format;
import static ch.autumo.ifacex.studio.ui.Messages.t;

label.setText(t("Add standard mapping"));                    // plain message
status.setText(format("Saved {0} ({1})", name, extension));  // with arguments
tooltip = new Tooltip(t("Create a new, empty configuration"));
```

Rules for new code:

* **Every** user-visible string goes through `t(…)` or `format(…)` — never a raw
  literal in a `Label`, `Button`, `Tooltip`, `TableColumn`, dialog or status line.
* `format(…)` uses `java.text.MessageFormat`, so `{0}`, `{1}`, … are arguments.
  **A message that contains literal braces must not go through `format(…)`** —
  MessageFormat would read `{source-field-1}` as an argument number. The mapping
  validation splits such a message into a `format(…)` part (the wrong value) and a
  `t(…)` part (the example with braces); see `FormBuilder.addMappingFromBox`.

## 12.5 Parameter labels

The metadata forms (`FormBuilder.mapGrid`) do not use the English label as the
message id — that label is *derived* from the configuration key and would change
whenever the derivation changes. Instead:

* the **message id is the raw configuration key** (e.g. `data_path`),
* the **derived English label is the fallback** (`t(id, english)`),

so a translation file can translate a parameter by its stable key and anything
not translated simply stays as it is:

```java
final String label = t(key, FieldCatalog.descriptor(key).label());   // "Datenpfad" or "Data path"
final Tooltip tip = new Tooltip(t(key + ".help", descriptor.help())); // help text: "<key>.help"
```

In the PO file such an entry carries the English label as an extracted comment:

```po
#. Data path
msgid "data_path"
msgstr "Datenpfad"

#. Path to the data array within the JSON response.
msgid "data_path.help"
msgstr "Pfad zum Daten-Array in der JSON-Antwort."
```

The keys are **technical identifiers and are never translated**; only their
labels and help texts are. Because the derived label is always shown when a
translation is missing, the parameter list in the catalog can grow without ever
leaving a field unlabelled.

## 12.6 Switching the language

The language is resolved **once at startup**, before the FXML is loaded
(`StudioApp.preInitialize`), in this order:

| Priority | Source | Example |
|---|---|---|
| 1 | system property | `-Difacex.lang=de` |
| 2 | app configuration `language` (autumo-ui `Constants.PROP_KEY_LANGUAGE`) | `language=de` in `ui/.../cfg/app.cfg` |
| 3 | app configuration `lang` (alias) | `lang=de` |
| 4 | default | `en` |

`Messages.setLanguage(…)` delegates to `Helper.setLanguage(…)`, which sets
`Locale.setDefault(…)` and the `user.language` system property, so the framework
(autumo-ui dialogs, the window title) follows the choice instead of the OS locale,
and reports how many entries the catalogue carries.

**English needs no real translation file:** English *is* the source language, so
for every normal message the `msgstr` would just repeat the `msgid` — `t(…)`
simply returns the message id (the English text) when the lookup finds nothing. A
language without a PO file behaves the same way. `messages.pot` is the template
that lists every message for translators.

`messages.en.po` exists nevertheless, but it carries **only the framework-key
overrides**: keys such as `application.name` and `About.title` are *not* English
text, so their English value has to be stored somewhere. Everything else in
`messages.en.po` would be redundant.

> Note: the Studio no longer ships a `lang/Bundle.properties` of its own. autumo-ui
> keeps its own bundle (`ch/autumo/ui/lang/Bundle*.properties`) as the **parent**
> of the PO bundle, so framework keys the Studio does not override still resolve
> (see §12.9.1).

## 12.8 Status
Translated today (185 messages): the whole shell (menu, toolbar, tabs, status
bar, file chooser, dialogs), the structural labels of every form (section
titles, captions, buttons, tooltips, table headers, hints, warnings) and the
**engine parameter labels and help texts** (via the key-as-msgid convention in
§12.5).

**Deliberately English (technical identifiers):** interface/type names
(`csv_in`, `rest_out`, `CSV`, `JSON`, `Mongo DB`, …) and the parameter keys
themselves, e.g. in the source-field list, the formula box and the raw views.
The `FieldCatalog` is still being rebuilt from the legacy parameter analysis
(see `docs/11-legacy-studio-gui-analysis.md` §7); new parameters automatically
become translatable because `mapGrid` translates every label and help text by key.

## 12.9 Live language switch (`Help › Language`)

Since §12.1 demanded that the OS locale must not leak in, a user on a German
machine that runs the Studio in English had no way back to German. The Studio now
offers the language at runtime: **`Help › Language ›` English / Deutsch**, each
with the framework's 16px flag icon (`lang_en.png` / `lang_de.png`). The language
names are written in their own language and are *not* translated.

`MainController.switchLanguage(lang)` moves **two catalogues** and then rebuilds
the screen:

| Catalogue | Call | Covers |
|---|---|---|
| autumo-ui framework resources | `Helper.setLanguage(lang)` | window title, About/license HTML panes, framework dialogs, JVM default locale |
| Studio texts (PO) | `Messages.setLanguage(lang)` | delegates to `Helper`; everything from §12.4/§12.5 |

Afterwards `applyTexts()` (static FXML shell), `buildToolBar()`, and — when a
configuration is open — `rebuild()` (navigation tree and the visible form) run
again, and `renderStatus()` re-renders the status bar, so no stale text is left
anywhere. `Help › Language` marks the active language with a radio dot; the
selection is applied programmatically at start-up, which does **not** fire
`onAction` in JavaFX.

### 12.9.1 One mechanism: PO lives in the framework

This answers an open question from the review: *should PO support move into
autumo-ui?* — **Yes, it did** (see §12.2):

* The **framework bundle** (`ch/autumo/ui/lang/Bundle*.properties`) is autumo-ui's
  own contract and **stays**: `Helper.getTranslatedText(app, "About.title")`, the
  framework's FXML panes (`defaultInfoPane.fxml`…) and its dialogs resolve there.
  It is now the **parent** of the PO bundle.
* The **application catalogue** is PO and is resolved **by the framework**. The
  Studio ships no `.properties` translations of its own any more; its catalogue
  lives at the application base resource path (`ui/…/ui/lang/messages.*.po`), so
  `Helper.getMessageBundle(…)` finds it for the framework's own lookups too.
* `core` is UI-free again: the old `core/i18n` package (parser + lookup) was
  deleted; the parser moved into autumo-ui.

autumo-ui also got a small, generic API so *any* autumo-ui application can switch
languages at runtime **and** only has to translate its own texts:

```java
Helper.setLanguage("de");              // default locale + user.language + bundle cache
String lang = Helper.getLanguage();    // never null; falls back to "en"
Helper.addLanguageListener(() -> …);   // re-apply application texts
```

The framework changes (all in autumo-ui, version stays `1.2.0`):

* `Helper.setLanguage/getLanguage/getSupportedLanguages/addLanguageListener` —
  the language is now an explicit framework state instead of being read ad-hoc
  from `user.language`. A region is ignored (`de_CH` → `de`), which matters
  because autumo-ui's own `Constants.LOCALE_DE` *is* `de_CH`.
* `Helper.getMessageBundle()` returns a **`PoResourceBundle`**: the application's
  PO catalogue (`<base>/lang/messages.<lang>.po`, parsed by the new
  `ch.autumo.ui.utils.PoFile`) is consulted first, then the `.properties` bundles
  (the application `Bundle` and the autumo-ui base bundle) as before. The bundle
  is cached per base/language and the cache is cleared on a language change
  (`Helper.setLanguage`), so the PO file is parsed once and not on every lookup.
  An application without any `lang/Bundle` is no longer treated as an error.
* `Helper.getMessageBundle()` also returns a `FallbackResourceBundle`: keys the
  application bundle does not define fall back to the autumo-ui base bundle.
  Before, an application had to copy every framework key (`button.Alright`,
  `dialog.*`, …) into its own bundle or the framework's panes failed with
  `MissingResourceException` — our self-test hit exactly that (see §12.10).
  An application may still override any framework text.
* `Helper.getText(app, id, fallback)` — a lookup that returns a fallback instead
  of throwing `MissingResourceException`. Needed for the Studio's metadata-driven
  texts, whose message id is a configuration key (§12.5).
* The framework's German bundle is `Bundle_de.properties` (was
  `Bundle_de_CH.properties`) so it is found for `de` *and* `de_CH`; the bundled
  HTML panes read the language through `Helper.getLanguage()`.
* `UI.showExceptionDialogExtended` now styles itself with the autumo-ui base
  stylesheet. Before, it built an app path (`<app>/style/application.css`) that
  no application ships, so the global uncaught-exception handler – installed by
  `BaseApp` for every app – ended in an `NullPointerException`.
* `Helper.getBaseStyleURL()` / `Helper.getBaseHTMLStyleURL()` had swapped
  bodies (the JavaFX stylesheet vs. the WebView stylesheet); they now match
  their names.

One dependency followed from this: the Studio's `ui` module must ship
`javafx-web` (Maven) because the framework renders About/license in a `WebView`;
without it the panes fail with `NoClassDefFoundError`/`ClassNotFoundException`.
